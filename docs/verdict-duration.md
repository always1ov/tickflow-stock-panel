# 结论列的「状态时长」—— 定义、判定规则、计算口径、展示

> R233~R237。用户: 「当某只股票进入候选状态(或其他自定义状态)时, 记录进入该
> 状态的起始日期, 并在结论列中展示从该日期起算的持续时长」。
>
> 这份是**口径文档**, 不是设计意图。凡是代码与本文不一致的, 以代码为准并回来改这里。
> 判定层的实现在 `indicators/keltner_geometry.py`(`verdict_codes` 交出逐日
> 结论序列, `count_trailing` 数尾部连续段), 接线在
> `services/keltner_service.py::channels_for_symbols`。

---

## 1. 「状态」是什么

**状态 = 通道结论(`keltner.verdict`)的那个 `code`。** 一共十档, 互斥:

| code | 标题 | 语气 |
|------|------|------|
| `top_all_bands` | 大顶区域 | sell |
| `bounce_in_downtrend` | 超跌反弹 | sell |
| `top_confirmed` | 该止盈了 | sell |
| `high_short_only` | 短线冲高 | hold |
| `watch_high` | 高位回落 | watch |
| `watch_low` | **候选池** | watch |
| `low_short_only` | 短线回调 | buy |
| `bottom_confirmed` | 调整到位 | buy |
| `dip_in_uptrend` | 强势深调 | buy |
| `falling_all_bands` | 下跌途中 | avoid |

**判定一个字都不是这一层写的** —— 全走作者的 `keltner.assess` + `keltner.verdict`
(`indicators/keltner.py` 是只读的)。这一层只回答「同一个 code 连着几天」。

### [R242] 没有结论的那一格也是一个状态

三档都在通道中部时, 底层 `verdict()` 返回 `None`。那一格徽标印的是**补充层
组合注记的标题**(「半年低位」, 见 R203), 只有「中中中」才真的印 `—`。

早先这一格一律不给时长, 理由是"没有结论就没有持续多久这回事"。**那条理由
站不住**: 用户看到的是「半年低位」—— 一个模糊的时间词, 偏偏没有天数。用户:
「别搞什么下跌半年, 下跌多少天就表示多少天」。

所以「状态」的定义扩一档 —— **徽标上印的是什么, 就数什么**:

| 徽标印的 | 状态键 | 天数挂在 |
|---|---|---|
| 结论标题(「候选池」) | 结论码 `watch_low` | `verdict.days` |
| 组合注记标题(「半年低位」) | 组合键 `combo:inside\|inside\|below` | `state_run.days` |
| `—`(中中中) | 组合键, 同上 | `state_run.days` |

两套用的是**同一条数法**(`count_trailing`, 尾部连续段)、同一个说法
(`已N天`)。这才对得上 §5.5「必须统一表达」。

**判定还是一个字都没动** —— 组合键是拿作者 `assess` 出来的三档 `pos` 拼的
(`state_key`), 不是新判定; 有结论时 `state_key` 原样返回作者的 `code`。

天数只有一份: 有结论时 `state_run` **不出现**(否则同一行会摆出两个数,
读的人得先判断哪个是哪个)。

## 2. 起止判定

```
起点   从今天往回数, 第一个与今天 code 不同的交易日的下一个交易日
终点   状态一直持续到今天(它就是"今天这一档")
中断   中间任何一个交易日的 code 不同 —— 包括"那天没有结论" —— 就重新起算
```

**中断即重算, 不累计。** 「候选池」出现 3 天、隔一天回到通道中部、再出现 2 天,
报的是 **2 天**不是 5 天。那是**两次独立的出现**; 报 5 天会让人以为它已经在这个
位置磨了一周, 而实际上刚回来两天。

> 这条与「在轨外连续几天」(`runs.above_run`)、六态的 `duration` 是同一条纪律 ——
> 整个系统里所有"连着几天"都是**尾部连续段**, 不是累计出现次数。

## 3. 时长怎么算

### 单位是**交易日**, 不是自然日

同一行里六态徽标写着「上涨趋势 已3天」, 那个数是交易日。两个天数并排摆着,
**必须可比** —— 一个按交易日一个按自然日, 用户没法把它们放在一起读。

停牌日不在日线里, 因此天然不计入。

### 含今天

今天这一档成立, 就是第 1 天。**没有"第 0 天"** —— 那不是人话。

### 回看范围

`VERDICT_TAIL = 250` 天。**窗口必须够它用**, 否则这个常数就是句空话:

    520 个自然日 ≈ 370 根 K
    − 120 根       长期档 MA120 的暖机(日线表只预计算到 ma60, 没有 ma120 列,
                   而 pipeline.py 是作者的、不能加, 所以这一档只能自己滚)
    ─────────────
    = 251 天       真正判得出结论的天数, 刚好盖住 VERDICT_TAIL

**[R244] 这里原来是错的。** 窗口只有 260 个自然日 ≈ 178 根 K, 扣掉 120 根暖机
**只剩 59 天**判得出结论 —— 一只挂了大半年的「候选池」, 徽标封顶就印 59。
用户: 「候选池显示的天数不正确」。

配套的上限判据也错着(见下), 所以那个 59 连 `+` 都不带, 看着像个准数。

> 逐日结论这一路**单独**吃 520 天(`_LOOKBACK_DAYS_VERDICT`); 压缩指数、
> 在轨外天数、频段能量仍旧只看原来那 260 天的切片 —— 它们的读数会被窗口
> 长度改变(实测 `compress_days` 从 59 跳到 250), 那是另一件事, 不该搭车。
> 切片锚在**这只票自己最后一根**上而不是 `date.today()`: 数据不新鲜时按今天
> 切会把几何那条路整段饿死。
>
> 实测 145 只自选: 260 天 434ms → 520 天 729ms。多花的 0.3 秒挂在 5 分钟
> 缓存一次的批量上, 换"数字是真的"。

### 上限(`capped`)怎么判

    hist >= judgeable_span(codes)      连续段数到了**判得出结论**的尽头

**[R244] 不是 `hist >= len(codes)`。** `len(codes)` 把暖机那 119 天(值是
`None`)也算在长度里, 所以这个判据**永远不成立** —— 被窗口截断的天数从来不标
下界。少一个 `+`, 一个下界就变成了准数。

### 数不出来的时候

历史里最近一根就不是这一档时(见 §5), 给 `days = 1, days_exact = false`。

**R240 起徽标上不再有问号。** 前提拿掉之后(见 §5)这种情形只剩一种成因 ——
**今天刚变成这一档** —— 那时「已1天」本来就是正确答案, 不是兜底。
`days_exact` 字段保留, 只在悬停里说明。

## 4. 更新时机

| | |
|---|---|
| **口径** | **收盘价**。盘中不改判 |
| **后端何时变** | 数据管线每日收盘后更新 enriched 快照; 下一次请求就是新值 |
| **前端何时拉** | `stockKeltner` 的 `staleTime = 5 分钟`; 切页/刷新/过期后自动重取 |
| **盘中会不会跳** | **不会** |

**盘中不改判是有意的**, 不是没做。通道要 ATR 与三条均线, 而实时叠加层只有价格
—— 拿实时价去比昨天的通道, 得到的是个半新半旧的判定。这条约定在决策台
「Keltner 三档位置」那一列上从 R42 起就立着, 时长跟着它走。

所以「实时更新」在这里的准确含义是: **每个交易日收盘后自动 +1, 状态一破立刻
归零重算, 不需要任何手动维护**。不是"盘中每秒变"。

## 5. 两条路对不上时怎么办(R239 已把这个前提拿掉)

今天这一档来自 enriched 快照(预计算的 ma20/ma60), 而逐日序列来自日线批量。
两条路在最后一根上**可能对不上** —— 数据日期差一天、末根不同、复权口径不同。

早先的写法要求两者先在"今天"上达成一致, 对不上就整个作废 ——
**那是一个必须成立、却经常不成立的前提**, 结果是全表每一行都退化成 1 天
(用户实测截图)。

现在没有这个前提了: `verdict_codes` 只交出**逐日结论序列**, 由
`channels_for_symbols` 拿**徽标上那一档**往回数(`count_trailing`)。
只有"历史里最近一根就不是这一档"时才落到 1 天, 而那通常正确 —— 今天刚变。

短/中档一律吃日线表的**预计算列** ma20/ma60(与复盘、徽标同源);
只有本来就没有预计算列的长档自己滚。

## 5.5 [R241] 时长的**统一说法** —— 全界面只有这两个词

用户: 「必须要统一表达, 不能又两种多种表述」。**这条是我的问题** —— 同一件事
当时在界面上有六种说法:

    上涨趋势 3天          决策台六态徽标
    调整到位 已12天        决策台结论徽标
    上涨趋势 第 11 天      复盘「现在」条与逐日表
    3天                   复盘段卡片
    已连着 12 个交易日      悬停卡片
    已经这样 N 天 / 连着 N 天  悬停里的重合、在轨外

同一行里六态写「3天」、结论写「已12天」, 读的人得先判断这两个数是不是一回事。

**从此只有两个词:**

| 词 | 含义 | 用在哪 |
|----|------|--------|
| **`已N天`** | 到今天**还在**这个状态, 已经 N 天 | 六态徽标 / 结论徽标 / 复盘「现在」条 / 逐日表 / 悬停 / 重合 / 在轨外 |
| **`持续N天`** | 历史上**那一段**总共多久(已结束) | 复盘的段卡片 |

两个词各有一个意思, 且**从不用于同一件事** —— 段卡片说「已」会被读成"到今天
还在", 而那一段可能早就结束了(用户截图里那只票最新一段是 16 天前的)。

数字上限用 `+`(徽标)或「以上」(悬停), 不再用 `≥`/`超过` 两套写法。

## 6. 展示

### 决策台「结论」列 / 今日总览

列很窄, 徽标上**只放数字**:

```
候选池 已12天       数出来的
候选池 已178天+     一段比能看到的还长, `+` 表示下界
候选池 已1天        今天刚变成这一档
半年低位 已181天     [R242] 没有结论那一格, 数的是三档组合本身
— 已181天           连「中中中」也带天数 —— 整列没有一个徽标是光秃秃的
```

### 悬停卡片(`VerdictHover`)

放能核对的那一份 —— **天数每天变, 起始日不会变**, 拿它可以回 K 线上核对
那一天到底发生了什么:

```
候选池   已12天 · 自 2026-08-14
```

悬停提示写明口径:「这是当前这一段连着多少个交易日, 不是历史累计。含今天;
中间只要断一天就从头重新起算」。

### 复盘弹窗里那个天数是**另一套**

`StockReviewDialog` 的段卡片写着「候选池 2026-09-07 ~ 2026-09-09 · 持续3天」
—— 那是**前端**从逐日行自己数出来的(`toSegments` + `rows.length`), R48 就有,
与本文说的这一套**互相独立**。

口径一致(都是尾部连续段、都按交易日), 但**来源不同**:
所以复盘里有天数**不能**用来判断本功能是否已部署。这一点让用户白排查过几轮。
措辞也刻意分开: 那是历史段, 用「持续N天」而不是「已N天」(见 §5.5)。

## 6.5 [R245] 这一类天数**全都**有天花板 —— 撞上了就要说

天数不是只有结论徽标一个。系统里每个"连着几天"都吃同一套约束:

| 量 | 天花板 | 撞上了怎么说 |
|---|---|---|
| 结论 / 组合 `days` | `VERDICT_TAIL = 250` | 徽标 `已N天+` |
| 磨底 `compress_days` | `MAX_LOOKBACK = 250` | `compress_capped` |
| 在轨外 `above/below_run` | 同上 | `above/below_capped` |
| 六态 `duration` | `WINDOW_TRADING_DAYS = 250` | `duration_capped` |

**四个上限刻意是同一个数。** 不然同一行里两个徽标各自封在不同的天花板上,
读的人无从分辨哪个数是真的。

天花板有三堵墙, 第三堵最阴 —— 它长在数据**中间**而不是尽头:

    · 回看上限          MAX_LOOKBACK / VERDICT_TAIL
    · 窗口就这么长       日线批量只取回这么多根
    · 算不出来的那些天   长期档 MA120 要 120 根暖机, 更早的行是 {} / None

原来 `_tail_run` 写的是 `if not r or not ok(r): break` —— 把第三堵墙和"这一段
自然结束"并成了一支, 于是撞墙的天数照样是下界, 却被当成准数印出去。
现在两支分开(见 `_tail_run`), 撞墙给 `capped=True`。

**六态那一路最露骨: 它零暖机**, 喂多少根就能数多少天。窗口取 180 时, 一只走了
两年上涨趋势的票印的是「已180天」—— 那不是天数, **是窗口长度本身**。

### 提前退出 —— 这些天数**不该**贵

用户: 「我的理解是这里不是已经有最新总结好的时间了吗, 怎么那么麻烦你还搞不定?」

对。`verdict_codes` 原来无脑算满 250 天, 而下游(`count_trailing` /
`judgeable_span`)**只读前导那一段** —— 两个都在第一个"与今天不同"的位置停下。
一段 25 天的「候选池」算 250 天, 十倍白工。

现在到第一个变化就收手, 多留**一个哨兵位**(`judgeable_span` 靠它区分
「段自己结束了」与「没得数了」)。实测 145 只自选:

    434 ms   修复前(数字是错的)
    729 ms   R244 加长窗口后
    236 ms   加提前退出 —— 比修复前还快一倍, 而数字是对的

16 个具名场景逐一比对: 提前退出前后, 天数与下界标记**完全一致**。

## 7. 测试守在哪

`backend/tests/test_verdict_run.py`:

- 刚出现 = 1 天, 不是 0
- 连着 N 天就数 N 天
- **中间断一天重新起算**(整个口径的关键那条)
- 换了一档从头起算
- 三档都在中部时 `verdict.days` 不给 0(那一格的天数走 `state_run`)
- **[R242] 没有结论那一格也有天数**: 组合键与结论码不会撞、有结论时
  `state_key` 原样返回作者的 code、有结论时不另给一个平级的 `state_run`、
  **端到端**拿得到 `state_run`、徽标文案同样是「已N天」
- 「候选池」这一档同样有天数(用户点名问过)
- **十条结论没有一条被排除**(盯实现里不许出现具体 code)
- 判定仍走作者那两个函数
- 数据不齐 / 暖机不足时安静返回, 不崩
- 两条路对不上时今天仍算 1 天(R234 那个静默失效)
- 只要有结论 days 就一定在(R236)
- **端到端**: 天数真的出现在 `channels_for_symbols` 的返回里(R235 —— 前面那些
  单元测试全绿而链路是断的, 就是这么漏过去的)
- 起始日 `since` 指向这一段的第一个交易日
- **[R244] 天数不再被暖机边界悄悄截断**: `judgeable_span` 只数判得出结论的天;
  被截断的段必须标下界、自己结束的段不许乱标; 上限判据不许退回 `len(codes)`;
  窗口够长期档暖机之后还数得满 `VERDICT_TAIL`; **加长窗口不许改动别的指标的
  读数**(16 个具名场景 × 11 个字段逐一比对)
